# Continuous Integration

`.github/workflows/ci.yml`. Every job is blocking — a pipeline with advisory jobs trains
people to ignore it.

## Jobs

| Job | Runs | Fails on |
|---|---|---|
| `lint` | `ruff check .`, `ruff format --check .` | Any violation |
| `types` | `mypy --strict app services` | Any error |
| `test` | `pytest -m "unit or api or security" --cov=app` | Any failure; coverage below floor |
| `integration` | Postgres service container, `alembic upgrade head`, `pytest -m integration` | Any failure |
| `security` | `pip-audit`, ruff `S` rules, `gitleaks` | Known CVE in a pinned dependency; any detected secret |
| `build` | `docker build`, boot the container, `curl /health`, Trivy image scan | Build failure, unhealthy container, HIGH/CRITICAL CVE |
| `eval-smoke` | `pytest -m evaluation` + a smoke evaluation run | Harness failure or invalid report |
| `lock-check` | `uv lock --check` | Lockfile out of date with `pyproject.toml` |

`lint`, `types`, `test`, `security` and `lock-check` run in parallel; `integration` and
`build` follow.

## Why `eval-smoke` is a CI job

Evaluation harnesses rot silently: nobody runs them between benchmark pushes, and by the time
someone needs a number the harness no longer imports. Running the smoke set on every push
keeps it executable. It is a **wiring test** — it asserts the harness produces a valid,
metadata-stamped report, not that any detection number is good
([ADR-006](adr/ADR-006-evaluation-methodology.md)).

## Caching

`uv` cache keyed on the hash of `uv.lock`, plus Docker layer caching for `build`. The cache
key must be the lockfile, never a date or a branch name — a cache key that does not change
when dependencies change is how a "green" pipeline tests the wrong dependency set.

## Secrets

**None.** The pipeline builds, tests and scans; it does not deploy. Deployment credentials
would make every fork's CI a credential-exposure surface, and the mock upstream means no
provider key is needed to run the full suite
([ADR-009](adr/ADR-009-mock-upstream.md)).

Optional real-provider contract tests are credential-gated and excluded from default CI; they
run on demand in a trusted context only.

Placeholders and documentation for deployment live in
[deployment.md](17-deployment-architecture.md).

## Branch protection (intended)

* All jobs green before merge.
* No direct pushes to `main`.
* Migrations reviewed by a human — an autogenerated Alembic revision is a draft, not a change.
* Any change to `app/policy/`, `app/detectors/` or `tests/security/` warrants explicit
  security review, because those are the files where a subtle change silently weakens the
  product.

## Failure triage

| Job | Usual cause |
|---|---|
| `lock-check` | `pyproject.toml` edited without `uv lock` |
| `types` | A new untyped dependency needs a stub or an override entry |
| `integration` | Postgres service not healthy yet — the job waits on `pg_isready`, not a sleep |
| `security` | New CVE in a pinned dependency; bump and re-lock rather than suppress |
| `build` | Trivy HIGH/CRITICAL — usually the base image; refresh the pinned digest |
| `eval-smoke` | Report schema changed without updating the harness test |

## Not in CI, deliberately

* **Load and soak tests** — too slow and too noisy on shared runners; run on demand
  (Phase 6), reported with machine metadata.
* **Full benchmark suite** — latency numbers from shared CI runners are meaningless
  ([performance-benchmarking.md](15-performance-benchmarking.md)); benchmarks run
  on a documented machine.
* **Model downloads** — Phase 2 models are large; CI uses a cached small fixture model, with
  the real model exercised in the on-demand evaluation run.
